# ADR-0008: プログラミング原則・テスト原則のスキル化とハーネスでの強制

- 状態: 採用
- 日付: 2026-10-10

## 背景

ハーネス（スクリプト・フック）が増えるにつれ、判断と I/O が混在し、ルールの重複やリポジトリ間のずれが生じた。
テストもリポジトリ外の使い捨てスクリプトでしか行っておらず、変更時に再検証されなかった。
実コードとハーネスの両方に、同じ品質基準を一貫して適用したい。

## 決定

- **原則をスキルとして定める。** `.claude/skills/programming-principles/`（SOLID・テスト可能性・YAGNI・可読性）と
  `.claude/skills/testing-principles/`（ISTQB の 7 原則・単体 → 結合 → 統合・同値分割・境界値・正常系／異常系・AAA）。いずれも厳守。
- **機械で検査できる項目はハーネスで強制する。**
  - スクリプト・フックごとのテストの有無、テストの AAA 区切り、シェル関数・ファイルの長さ、ShellCheck → `scripts/check-principles.sh`
  - Rust 関数の長さ → clippy `too_many_lines`（40 行）
  - テストレベルの順序 → `scripts/check.sh` が静的検査 → 単体 → 結合 → 統合の順に実行し、失敗した段階で止める
- **機械で検査できない項目**（O/L/I/D・YAGNI・テスト設計・ISTQB の原則）は、スキルのチェックリストと PR テンプレートで自己レビューする。
- **ハーネス自体を原則に沿って作り直す。** 判断は純粋関数（`scripts/lib/policy.sh`）、入出力はアダプタ（`hook-io.sh`）、
  リポジトリ固有の値は `scripts/harness.conf` に分離する（依存性逆転）。テストは bats で単体・結合・統合に分けて置く。
- **関連リポジトリとはコピーで共有する。** `scripts/lib/shared-files.txt` のファイルは同一に保ち、`check-shared-sync.sh`（CI）で照合する。
  共通化の仕組み（専用リポジトリ・プラグイン配布）は利用先が 3 つ以上になった時点で検討する（YAGNI）。

## 結果

- 原則違反の多くがローカルと CI で機械的に検出される。
- TypeScript の関数長・複雑度の機械検査は、web のコードが増えた時点で ESLint を導入して追加する（現時点では YAGNI）。
- ハーネスを変更するときもテストとスキルのチェックリストが必要になり、変更コストは上がるが、ずれと退行を防げる。
