# ADR-0022: 安定版・リリース候補版・プレビュー版の 3 系列を、2 本のブランチで 1 人で回す

- 状態: 提案
- 日付: 2026-11-06
- 改訂する ADR: ADR-0007（ブランチの役割と `dev` → `main` の時期）、ADR-0020（公開する系列と公開のしかた）

## 背景

0.1.0-rc.1（2026-10-22 公開）の後に 0.2.0 の alpha・beta を `dev` で出してきた結果、次のことが分かった。

- 正式版を出す手順（「段階の接尾辞を外す変更を `dev` → `main` で入れる」）が使えない。`dev` には 0.2.0-beta が入っていて、0.1.0 に混ざる。
- 公開できる URL は安定版とプレビュー版の 2 つしかない。0.3.0 の alpha を出すと、プレビュー版は最も新しい 0.3.0-alpha を指す。0.2.0 の rc はどの URL からも開けなくなり、試してもらう期間が成り立たない。
- リリースを公開すると、そのタグのコミットにある `pages.yml` が動く。0.1.0-rc.1 のコミットには系列を分ける仕組み（ADR-0020）が無い。そのため、このコミットから 0.1.0 を出すと、サイトが 0.1.0 だけで丸ごと置き換わり、`/preview/` が消える。
- 公開のたびに、すべての系列をそのタグから作り直してテストし直している。古いタグの道具が新しい環境で動かなくなる（Node.js 26 で 0.1.0-rc.1 のテストが落ち、#202 で版ごとに Node.js を選ぶ仕組みを足した）。

開発はメンテナ 1 人と AI エージェントで行う。古い系列にパッチを出し続ける余力は無い。
利用者が増えても仕組みを変えずに済む形として、他のプロジェクトのやり方を調べた。

- **大きなプロジェクト**（Rust・Node.js・Kubernetes・CPython・VS Code）は、系列ごとにブランチを持ち、本線で直した修正を古い系列へ 1 本ずつ写す。
- **小さなプロジェクト**（Joplin・Penpot・Excalidraw・SysML v2 の公式実装）は、最新だけを直す。
- **Web エディタ**は、系列ごとに URL を分ける（VS Code の vscode.dev と insiders.vscode.dev）。古い版を開ける URL を出しているものは見つからなかった。

## 決定

### 1. 系列と URL

| 系列 | URL | 置く版 | 保存領域の名前の後ろ |
| --- | --- | --- | --- |
| 安定版 | `/modelith/` | 最新の正式版 | （付けない） |
| リリース候補版 | `/modelith/rc/` | 正式版がまだ出ていない、最新の rc。無いときは「今は候補の版はありません」と安定版へのリンクだけを置く | `@rc` |
| プレビュー版 | `/modelith/preview/` | 段階によらず、最も新しい版（今と同じ） | `@preview` |

- 系列は、人が選ばず、公開済みのリリースのタグから機械的に決める（`web/tools/channels.ts`）。下書き・番号の形でないタグは選ばない。
- プレビュー版の意味は変えない。rc.1 を出した直後で、次の alpha がまだ無いときは、プレビュー版とリリース候補版は同じ版になる（保存領域は別）。
- 古い版を開ける URL は持たない。困ったときの戻し方は 4 に書く。

### 2. ブランチと修正の流し方

| ブランチ | 中身 | 付けるタグ |
| --- | --- | --- |
| `dev` | 次の版の開発。トピックは今までどおり Squash で入れる | alpha・beta |
| `main` | 候補と安定版。rc の間の修正と、安定版への急ぎの修正 | rc・正式版・パッチ（`X.Y.Z`） |

- **`dev` → `main` をマージするのは、次の版の rc.1 を出すときだけ**にする。前の rc が正式版になるまでは行わない。同時に進む候補は 1 つだけにする。
- **rc の間の修正**は、`main` から `fix/*` などを作り、`main` に向けて PR を出す。`main` へのマージには、今までどおり毎回メンテナの許可が要る。
- **`main` に入ったものは、すぐに `main` → `dev` をマージして戻す**（マージコミット、許可は要らない）。戻す PR は、`main` への push を受けて自動で開く。
  `dev` でリリースの下書きを作るときに、`main` が `dev` の祖先でなければ止める。こうして「候補で直したのにプレビューで直っていない」を防ぐ。
- **修正を出すのは最新の系列だけ**にする。古い正式版の系列にはパッチを出さない。
  - 候補が進んでいないときの安定版の修正は、`main` で直して `X.Y.(Z+1)` を出す。rc を経るかはメンテナが決める。
  - 候補が進んでいる間の安定版の修正は、その候補に入れて次の正式版で届ける。
  - 例外として、データを失う不具合や安全の問題で待てないときだけ、メンテナの判断で安定版のタグから一時的なブランチを作ってパッチを出す。出したら消す。
- beta は今までどおり `dev` に付け、機能を固定する。beta の間は、次の版の機能を `dev` に入れない。

大きなプロジェクトとの違いは、写し先が `dev` の 1 本だけなことだけである。
写し先が 1 本なら、修正を 1 つずつ写すより、`main` から `dev` へまるごとマージするほうが簡単で、入れ忘れも Git の祖先関係で検出できる。
古い系列も直す余力ができたら、`main` の代わりに `release/X.Y` を版ごとに切れば、大きなプロジェクトの形に広げられる。3〜5 の仕組みはそのまま使える。

### 3. 版とブランチの検査

次のことをハーネスと CI で確かめる。

- **向け先と元**：PR の向け先と元の組み合わせ（`scripts/check-pr-base.sh`）。
  - `main` へは、`dev`（rc.1 の始まり）と、`fix/*`・`docs/*`・`test/*`・`ci/*`・`chore/*`（rc の間の修正と版の書き換え）だけを受け付ける。
  - `feat/*`・`refactor/*` は `main` に入れない。
- **マージの方式**（`guard-merge.sh` とルールセット）：
  - トピック → `main` は Squash
  - `dev` → `main` と `main` → `dev` はマージコミット
- **版とブランチ**：`dev` で作る下書きは alpha・beta だけ、`main` で作る下書きは rc・正式版だけにする（今の `scripts/release-draft.sh` を広げる）。
- **版の一致**：タグ、`Cargo.toml`・`web/package.json` の版、画面に出す版が同じであること。
- **番号の使い回し禁止**：一度出した番号は使い回さない。失敗したら次の番号で出し直す。

### 4. 組み立てと公開

- **作るのは 1 回だけ**：版ごとのアプリは、その版のリリースを公開したときに 1 回だけ作ってテストし、成果物をリリースに添付する。
  - 添付するもの：系列ごとのアプリ（例：`modelith-web-v0.2.0-rc.1-rc.tar.gz`）とテストのレポート。
  - 作る組み合わせは段階から決まる：alpha・beta はプレビュー版、rc はリリース候補版とプレビュー版、正式版は安定版とプレビュー版。
  - 作るときは、そのタグの中身を、そのタグの `.nvmrc` の Node.js で動かす。
- **公開は並べるだけ**：Pages への公開は、系列ごとの版を選び、添付された成果物を取ってきて並べるだけにする。古い版を作り直したり、テストし直したりしない。
  - #202 の「公開のたびに版ごとに Node.js を選ぶ」仕組みと、ADR-0020 の「安定版は落ちたテストを 1 回やり直す」決まりは要らなくなる。
  - 成果物が添付されていない版（この ADR より前のタグ）を選んだときだけ、その場で作って添付してから並べる。
- **公開は常に `dev` の定義で行う**：
  - `github-pages` の公開先は `dev` ブランチだけに絞る（今の `main`・`v*` を外す）。
  - これにより、タグのコミットの古い `pages.yml` が動いても、公開の段階で拒まれ、サイトは変わらない。
  - 新しいタグの `pages.yml` は、リリースの公開を受けて `dev` の公開のワークフローを起動するだけにする。
  - 手で公開し直すときも、`dev` から起動する（今と同じ）。
- **ロールバック**：正式版や候補を取り下げるときは、そのリリースを下書きに戻して公開し直す。選び直しで 1 つ前の版に戻る。作り直しは要らない。

### 5. マニュアル

- マニュアル（modelith.github.io）は、今の 2 つの版のままにする。
  - `/` は安定版の説明。
  - `/next/` はプレビュー版の説明。リリース候補版の機能はプレビュー版の一部なので、`/next/` で読んでもらう。
- `/next/` には「まだ正式に出ていない版の説明です」の印を出し、検索エンジンに載せない（`noindex`）。
- アプリの「ヘルプ」は、安定版なら `/`、リリース候補版とプレビュー版なら `/next/` へつなぐ。
- 正式版を出したら、`/next/` を `/` に写す（今の `copy-version.mjs`）。古い版のマニュアルは残さない。

### 6. ここまでの版からの移り方

1. この ADR と ADR-0023 を採用する。
2. 4 の公開の仕組みと、`/rc/` の系列と保存領域を `dev` に入れる。`github-pages` の公開先を `dev` だけにする（メンテナが設定する）。
3. ADR-0023 の互換の修正を `main` に入れ、`0.1.0-rc.2` を出す。`main` → `dev` に戻す。
4. 試してもらう期間を置いて、`0.1.0` を出す。0.1.0-rc.1 のコミットからは直接出さない（背景の 3 つめの問題のため）。
5. `0.2.0-rc.1` で `dev` → `main` をマージする。

## 検討した案

| 案 | 内容 | 採らなかった理由 |
| --- | --- | --- |
| 公開は 2 系列のまま | 候補の間は次の alpha を出さない | 利用者が増えると、試したい人と待ちたい人を同時に支えられない。後から URL を足すと保存領域も分け直しになる |
| 系列ごとに `release/X.Y` を切る | `main` の役を版ごとのブランチが持つ | 修正を最新にしか出さないなら、`main` と同じことをブランチの名前を変えながら行うだけになる |
| 本線で直して古い系列へ写す | 大きなプロジェクトの形 | 写す作業・承認・入れ忘れの検出が系列の数だけ要り、1 人では回らない |
| beta から `main` で仕上げる | `dev` を beta の間も止めない | beta を置く URL が要る（リリース候補版に混ぜると名前と合わない）。1 人の開発では、beta の間に次の版の機能を並行して入れる場面が少ない |
| 古い版を開ける URL（`/v/0.1/`） | 新しい版で困った人が戻れる | 古い系列を直さない前提では、戻った先も直らない。保存領域とマニュアルも版の数だけ要る |

## 結果

- 安定版・リリース候補版・プレビュー版を同時に公開でき、`dev` は beta の間を除いて止まらない。
- メンテナの手作業は、今までどおり `main` へのマージの許可とリリースの公開だけで、増えない。
- 古いタグの `pages.yml` は、公開の段階で必ず拒まれる。
- 公開のたびに古い版を作り直さないので、公開が速くなり、古い版の道具が動かなくなっても困らない。
- 古い正式版の系列には修正が届かない。困った人には、次の正式版を待つか、リリース候補版を使ってもらう。
- `main` は「最後に出した版」ではなく「候補と安定版を仕上げる場所」になる。ブランチ戦略・リリース手順・SECURITY.md の「修正を出す版」を合わせて直す。
