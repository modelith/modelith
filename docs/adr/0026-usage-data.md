# ADR-0026: 利用状況の送信

- 状態: 採用（2026-11-12）
- 日付: 2026-11-12
- 関連する ADR: ADR-0012（クラウド保存）、ADR-0024（AI と共同編集の土台）、ADR-0025（サーバの境目）

## 背景

どの機能がどれくらい使われているかが分からないと、何を先に作るかを決められない。今は、GitHub のスター、マニュアルのサイトの訪問数、ダウンロード数くらいしか手がかりが無い。

一方、要求 C-2 は、モデルや操作の情報を利用者が選んだ保存先以外に送らないとしている。また、Modelith を使う人には、モデルを外に出せない会社の人も多い。

ほかの OSS は次のようにしている。

| 製品 | 既定 | 送るもの | 止め方・確かめ方 |
| --- | --- | --- | --- |
| n8n（自分で動かす版） | 送る | 実行の回数、使ったノードの種類、版、失敗のエラーコード。中身と認証情報は送らない | 環境変数（`N8N_DIAGNOSTICS_ENABLED=false`） |
| Grafana | 送る | 版・OS・使った機能の名前と回数。値や中身は送らない。IP アドレスは残さない。送り先は自分たちのサーバ | 設定・`DO_NOT_TRACK`。送る中身を送らずに記録へ出す設定がある |
| Penpot（自分で動かす版） | 管理者が有効にしたときだけ | 匿名の利用状況 | フラグ |

法律の面では、次のことが言える（弁護士の確認は公開の前に受ける）。

- 日本の電気通信事業法の外部送信規律は、端末から外へ情報を送らせるときに、公表・通知・同意・オプトアウトのどれかで確認の機会を与えることを求める。
- EU の ePrivacy 指令（5 条 3 項）は、端末の情報を読む・送らせるときに、原則として事前の同意を求める。Cookie を使わない解析が例外になるかは、まだ決着していない。GDPR では、個人に結び付く情報なら、異議を唱える権利がある。

## 決定

### 1. 既定で送り、必ず止められるようにする

| | ブラウザのアプリ | 自分で動かすサーバ（0.5.0 から） |
| --- | --- | --- |
| 既定 | 送る（VS Code と同じく、すべての利用者に最初に一度知らせる。地域で分けない） | 送る |
| 段階 | 「すべて送る」「エラーだけ」「送らない」から選ぶ（VS Code の `telemetry.telemetryLevel` に倣う） | 同じ 3 段階 |
| 送るもの | 下の 5 の表 | 下の 5 の表 |
| 止め方 | 設定。最初に一度だけ、送ることと止め方を知らせる | 環境変数と `DO_NOT_TRACK=1` |
| 確かめ方 | 設定の画面で、送る中身を見せる | 送る中身を、送らずに記録に出す設定 |

### 2. 送らないもの

- モデルの中身・要素の名前・ファイル名・フォルダ名・プロジェクト名・エラーの文。
- 端末に残す ID（ブラウザのアプリでは、Cookie も保存領域の ID も使わない）。
- IP アドレスを、受け取った側で残さない。

### 3. 受け取り先は自分たちのサーバにする

- Google Analytics などの外部の解析サービスを使わない（送り先が増え、利用者に説明しにくく、EU では国外移転の問題にもなりうる）。
- 受け取り先は、Modelith のプロジェクトが動かす専用の受け口にする。受け取る項目は、この ADR の一覧に限り、知らない項目は捨てる。
- 受け取り先と項目は、マニュアルとプライバシーポリシーに書く。

### 4. 項目の一覧は 1 か所で決める

送る項目の一覧（名前・値の型・意味）を、plugin-sdk の契約（ADR-0024 の 2）に置き、アプリ・サーバ・受け口が同じ一覧を使う。項目を足すときは、この ADR か後に続く ADR で決め、マニュアルの一覧も直す。

### 5. いつ・何を送るか

送る間隔は Grafana に倣い、手元で回数を足し込んで日に 1 回まとめて送る。エラーだけは起きたときに送る。

**ブラウザのアプリ**

| いつ | 何を | 何のため |
| --- | --- | --- |
| 起動したとき | 版と系列（安定版・候補版・プレビュー版）、ブラウザと OS の種類、画面の幅の区分（スマホ・タブレット・パソコン）、表示の言語 | 開発（どの環境で試すか）、運用（新しい版への移り方） |
| その日に初めて起きたとき | 使い始めの段階（サンプルを開いた・テキストを書いた・図を開いた・保存した・フォルダを開いた） | 事業（使い始めた人がどこで止まるか） |
| 使うたび（回数を足し込む） | 図の種類ごとの表示、操作（追加・関係・名前の変更・削除・元に戻す）、エクスポートの形式、チェックの実行と問題の数の区分、プラグインの利用（公開の登録簿にあるものだけ名前を送る）、AI の書き換え | サービスの向上（何が使われ、何が使われないか） |
| 測ったとき | 起動の時間の区分、解析の時間の区分（ファイルの大きさの区分ごと）、wasm を読み込めなかった回数 | 開発・運用（遅い・動かない環境を見つける） |
| 続けて使っているか | このブラウザで使った週の数の区分、初めて使った月 | 事業（続けて使われているか。ID を持たずに測る） |
| エラーのとき（すぐ送る） | エラーの種類と、コードの場所（スタックトレース。利用者の文字は取り除く） | 開発（不具合を早く見つける） |

**自分で動かすサーバ（日に 1 回）**

起動ごとに作るランダムな ID、版、OS、動かし方（Docker・実行ファイル）、ログインの方式（管理者が作るアカウント・OIDC）、利用者の数、7 日以内に使った人の数、プロジェクトの数、保存容量の区分、プラグインの数。

### 6. 不具合の報告

「ヘルプ」に「不具合を報告」を置く。版と環境を書き込んだ GitHub の Issue の下書きを開き、利用者が中身を見てから送る。モデルの中身は書き込まない。

### 7. マニュアルのサイト

マニュアルのサイト（modelith.github.io）の訪問数は、アプリとは分けて、Cookie を使わない解析と Google Search Console で見る。

## 決めたこと（メンテナの判断、2026-11-12）

- 送る項目とその時期は 5 の表。不具合の報告は 6
- EU の利用者を地域で分けない。VS Code に倣い、全員に最初に知らせ、3 段階で選べるようにする（公開の前に弁護士に確かめる）
- 送る間隔は Grafana に倣い、日に 1 回。エラーだけはすぐ送る
- 最初の知らせの文は、作るときに画面の言葉の手引きに従って決める

## 結果

- 要求 C-2 を ADR-0025 の結果の文に書き換える（利用状況とエラーの送信はこの ADR に従う）。外部の CDN やアクセス解析を使わないことは変えない。
- 利用状況の送信の要求（送ること・止め方・確かめ方・送らないもの）を、要求仕様に足す。
- マニュアルに、送る項目・止め方・受け取り先を書く。
