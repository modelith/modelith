# ADR-0027: 画面と文書の言語（英語と日本語、その先の多言語）

- 状態: 提案
- 日付: 2026-11-13
- 関連する ADR: ADR-0008（原則をハーネスで強制する）、ADR-0014（画面の言葉）、ADR-0016（Rust のモデルと Worker）、ADR-0022（3 つの系列）、ADR-0024（AI と共同編集の土台）、ADR-0026（利用状況の送信）

## 背景

Modelith の画面と文書は、日本語だけで書いてきた。SysML v2 を使う人の多くは日本の外にいて、英語の画面と文書が無いと試してもらえない。
メンテナは、英語と日本語に対応し、いずれはほかの言語にも広げたいと考えている（2026-11-13）。

今の文言の置き場所は次のとおり（テストとコメントを除いた、日本語を含む行の数）。

| 置き場所 | 量 | 例 |
| --- | --- | --- |
| Web アプリの TypeScript（`web/src`） | 約 110 ファイル・約 1,000 行 | トースト・ダイアログ・ツールチップ・メニュー |
| `web/index.html` | 約 100 行 | 画面の骨組みのボタン・見出し |
| Rust のコア（`crates/*/src`） | 約 700 行 | 問題一覧の文（構文エラー・参照切れ・トレースの抜け）、設定ファイルのエラー |

文書は、利用者向け（マニュアルのサイト・README・CONTRIBUTING・SECURITY・リリースノート）と、開発者向け（ADR・要求仕様・開発の手順・対応表）に分かれる。
README・CONTRIBUTING・SECURITY は、2026-11-13 に英語を主にし、日本語のページを並べた（plugin-sdk と同じ形）。

## 決定

### 1. 進め方

| 版 | すること |
| --- | --- |
| 0.3.0 | **土台**。この ADR を採用し、文言を言語ごとの辞書に移す仕組みを作り、今の文言を移す。画面は日本語のまま |
| 0.4.0 | **英語版**。英語の辞書を入れ、言語を選べるようにする。マニュアルの英語版を、安定版のページから作る |
| その先 | ほかの言語。翻訳を受け付ける手順（辞書のファイルへの PR、または翻訳のサービス）を決める |

文書は、利用者向けを先に英語と日本語の両方にし、それが終わってから開発者向けに広げる（メンテナの判断、2026-11-13）。

### 2. 辞書（文言の置き場所）

- 文言は、言語ごとの辞書ファイルに、キーと文で置く（例：`web/src/locales/ja.json` の `"export.done": "「{name}」をエクスポートしました"`）。コードには文を書かず、キーと値を渡す。
- 値の差し込みは `{name}` の形にする。数で形が変わる言語（英語の単数・複数など）は、ブラウザと Node が持つ `Intl.PluralRules` で選ぶ。新しい npm の依存は足さない。
- 辞書の形は、翻訳のサービス（Weblate・Crowdin など）がそのまま読める、平らな JSON にする。
- キーが無い言語では、日本語の文を出す（英語の辞書がそろうまでの間）。英語の版を出す前に、キーの抜けを検査で無くす。

### 3. コアの文（問題一覧など）

問題一覧の文は、コア（Rust）が作り、ブラウザ・CLI（`modelith check`）・MCP が同じ文を出す（ADR-0024）。

- コアの問題は、今の `msg`（文）に加えて、**キーと値**を持つようにする。文はコアが辞書から作る（コアの辞書は crate の中に置き、ビルドで組み込む）。
- 言語は、呼ぶ側（画面・CLI の引数・MCP の設定）がコアに渡す。コアは端末の設定を読まない。
- 問題の種類のコード（`trace.derive` など。F-EDIT-11）は、言語によらず同じにする。AI と検査ルールは、文ではなくコードで判断できる。

### 4. 言語の選び方

- 最初は、ブラウザの言語（`navigator.languages`）が日本語なら日本語、それ以外は英語。
- 「設定」で選び直せる。選んだ言語は、このブラウザの設定に置く（プロジェクトの設定には置かない。同じプロジェクトを違う言語の人が開くため）。
- CLI と MCP は、引数・環境変数（`LANG`）の順で決め、無ければ英語にする。

### 5. 言葉の手引き

- 画面の言葉の手引き（ADR-0014）は、どの言語にも当てはめる。図の言葉を先に、SysML v2 の用語は補足に回す。
- 英語の手引きを、日本語の手引きの隣に置く。英語では、SysML v2 の英語の用語（part・requirement など）が一般の言葉と重なるので、どこまで言い換えるかを英語の手引きで決める。
- 図に描く記号（`«part def»` などのステレオタイプ）は、言語によらずそのまま描く。

### 6. ハーネス（ADR-0008）

- 移し終えたフォルダから順に、コードに日本語の文が直接書かれていないことを検査する（コメントとテストを除く）。
- 言語ごとの辞書のキーがそろっていること、差し込む値の名前が言語の間で同じことを検査する。
- e2e と UI テストの基準画像は、日本語のまま撮る。英語の画面は、言語を切り替える主な流れだけを確かめる。

### 7. 文書

| 文書 | 英語と日本語 | 置き方 |
| --- | --- | --- |
| README・CONTRIBUTING・SECURITY | 済み（2026-11-13） | 英語を `*.md`、日本語を `*.ja.md` |
| マニュアルのサイト | 0.4.0 から | VitePress の言語の切り替え（`locales`）。日本語は今のパス（`/`）のまま、英語を `/en/` に置く。版のフォルダ（安定版・プレビュー版）ごとに両方の言語を持つ |
| リリースノート | 0.4.0 から | 英語と日本語を 1 つのリリースに並べる（GitHub のリリースは 1 つしか本文を持てないため）。書き方は release のスキルで決める |
| 例のモデル・サンプル | 0.4.0 から | 英語の画面では、英語の名前のサンプルを開く（自分で作る。モックのサンプルは使わない） |
| 開発者向け（ADR・要求仕様・開発の手順・対応表） | 利用者向けが終わってから | 置き方は、そのときに決める |

## 決めること（採用の前に）

- 辞書の形：平らな JSON と `{name}` の差し込み（推奨）か、ICU MessageFormat か、Fluent か
- コアの文：コアが辞書から文を作る（推奨）か、コアはキーと値だけを返し、画面・CLI・MCP がそれぞれ文にするか
- マニュアルの英語版のパス：日本語を `/` のまま英語を `/en/` に（推奨）か、英語を `/` にして日本語を `/ja/` に移すか（今のリンクが変わる）
- 英語の画面で、SysML v2 の用語をどこまで言い換えるか（英語の手引きで決める）

## 結果

- 0.3.0 のあと、文言を足すときは辞書に書く。日本語の文をコードに直接書くと、検査で止まる。
- 0.4.0 で、英語の画面とマニュアルを出せる。ほかの言語は、辞書を足すだけで加えられる。
- 要求仕様に、言語の要求（画面の言語を選べる・問題一覧の文が選んだ言語で出る・CLI と MCP の言語）を足す（採用のとき）。
